# v0.2b — `bash`, with a command policy

**Status: complete and verified live.** 522 tests, all gates green, and the two acceptance
properties checked against the real thing: a non-interactive run could inspect the repo but **could
not** delete a directory, and read-only commands ran unattended.

**Goal:** complete the tool surface, and do it honestly about the fact that a shell is the most
dangerous thing in the box.

`research/02` §2 lists seven tools; five exist. `bash` is the sixth. It is also the one that can do
anything, so most of this milestone is about *deciding when it may run unattended* rather than about
running it.

**Not in this milestone:** compaction (the default model has a 1M context, so a long run overflows
nothing yet — revisit when eval runs or smaller models make it bite), `web_fetch`, and background
processes.

---

## 1. Decisions

| Decision | Choice | Why |
|---|---|---|
| Sandboxing | **None in-process.** Confine `cwd`, drop stdin, cap time and output; isolation is a container's job | pi ships no sandbox and says why: partial isolation is mistaken for a boundary while still depending on the host shell and credentials ([r02] §8, `research/01` §permissions) |
| Interactive commands | `stdin=DEVNULL` | An interactive subprocess *hangs* the run. `research/02` §7: needs background+poll instead, which is a later feature; failing fast is honest |
| Timeout | 30 s default, 300 s hard ceiling, kill the **process group** | A timed-out shell that leaves children running is worse than no timeout |
| Output | 16 KB budget, **head + tail** elision, spill past 4× | `research/02` §2: an unbounded command can return half a window; mini-SWE-agent elides with head/tail rather than truncating the tail |
| Approval | **Read-only commands run unattended; everything else asks** | A prefix allowlist is the only thing that can be *proven*; anything unprovable asks. Deny beats allow |

## 2. The command policy

`research/01` §permissions: Codex is the only surveyed harness with a declarative policy language
(`prefix_rule` in Starlark, with `match`/`not_match` load-time tests). This is a small version of it.

```
read-only (no approval)   ls cat head tail wc file stat tree
                          grep rg find fd
                          git status|diff|log|show|branch|remote|blame|ls-files|rev-parse
                          pytest --collect-only   uv run pytest --collect-only
                          python -m py_compile (single file)   # parse check, no side effects
everything else            asks
```

Two rules that matter more than the list:

- **Unprovable ⇒ ask.** Shell metacharacters (`;`, `&&`, `||`, `|`, `` ` ``, `$(`, `>`, `>>`, `<`)
  make a command's effect undecidable by prefix, so anything containing them asks, even if it starts
  with an allowed word. `cat a.txt > b.txt` must not pass as `cat`.
- **The allowlist is a floor, not a ceiling.** A user can add prefix rules via config; a rule can
  only ever *add* read-only prefixes, never grant approval to something the policy would refuse.
  Matches the "hooks cannot upgrade a permission" rule.

Each rule carries `match`/`not_match` examples that are checked at load time, so a bad regex fails at
startup rather than silently allowing or refusing the wrong thing years later.

## 3. What a checkpoint cannot cover

`edit` and `write` take a pre-image before changing anything. `bash` cannot: we do not know which
files a shell command will touch, and guessing would be worse than admitting it.

So an approved `bash` call records `checkpoint: "not-possible"` in the log, and git remains the
second store for that class of change. The approval prompt says so, because the user's decision is
different when undo is unavailable.

## 4. Build order

| Step | Deliverable | Test |
|---|---|---|
| 1 | `command_policy.py`: prefixes, metacharacter rule, match/not_match validation | `cat x > y` asks; `git status` does not; a bad rule fails at load |
| 2 | `bash.py`: run, timeout, process-group kill, head+tail elision, spill | timeout kills children; huge output is elided with counts; exit code reported |
| 3 | gate wiring: `approval_required(args, ctx)` on the Tool protocol | a read-only command skips approval; a metacharacter command does not |
| 4 | docs + system prompt | the model knows the rule |

## 5. What building it found

1. **My own rule validation caught two bad rules.** `find` had `not_match=("find . -delete",)`, which
   is incoherent: a prefix rule matches by prefix, so claiming not to match a command that starts
   with it makes the rule lie about itself. The right mechanism is a per-rule ``deny_tokens``, because
   a prefix cannot express "unless a later flag makes it destructive".
2. **A global dangerous-token list was over-broad and included `-r` and `-f`.** That would have sent
   `grep -r` and `ls -f` to the user for approval. A gate that cries wolf gets bypassed, so the list
   is now short and command-specific destructiveness lives in the rule — `git branch -D`,
   `git show --output=file`, `find -delete`.
3. **Deny tokens missed `--output=file`.** Flags are routinely written with an inline value, and an
   exact comparison silently misses the most common spelling.
4. **The gate applied the path policy to every mutating tool**, so `bash` was refused with
   "path is empty" before the command policy ever ran — a guard that was right about the shape of a
   file tool and wrong about the shape of a shell. The path policy now applies only to tools that
   name a path.
5. **`bash` was left unregistered** when the registry tuple was reformatted, and the only symptom was
   "unknown tool 'bash'". The registry is now a named tuple so a patch cannot half-apply.

One thing that needed no fixing and is worth recording: the policy caught
``ls -la; du -sh build`` — a plausible-looking inspection command — purely because of the `;`, which
is exactly the case the metacharacter rule exists for.

## 6. Acceptance

1. `pytest -q` runs unattended in the TUI; `rm -rf build && ls` asks.
2. A command that never exits is killed at the timeout, with its output preserved and stated.
3. A command producing megabytes returns a head+tail view, the elided count, and a spill path.
4. A non-interactive run cannot execute a non-read-only command without `--allow-writes`.
5. The log records the command, the decision, the exit code, and whether a checkpoint applied.
