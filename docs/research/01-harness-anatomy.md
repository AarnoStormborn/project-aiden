# Anatomy of a Production Coding-Agent Harness

> What actually sits between a model and a terminal: the loop, the prompt build, the context
> lifecycle, the transcript store, the guard chain, the delegate plane, the stream, the error
> taxonomy, and the bill. Compared across Pi, Claude Code, OpenClaw, Aider, OpenHands, Codex CLI,
> opencode, Goose and SWE-agent as of mid‑2026.

## TL;DR

- A harness is **nine layers**, and the only one that is genuinely model-dependent is L1 (transport).
  Everything above it is a state machine, a store, and a policy chain [4][26].
- Loop implementations converge on the same shape: `assemble → stream → parse tool calls → gate →
  execute → append → repeat`, with the differences living in *where recovery is encoded* — Claude
  Code's 7 `continue` paths in one 1 729‑line `query.ts` [17], Pi's event-emitting `runLoop` [2],
  Goose's module-per-state machine [49], OpenHands' event-sourced `Agent.step` over an event log [36].
- Tool execution is **two nested loops**, not one: prepare (validate + gate) then execute, and the
  ordering of *result emission* (completion order) vs *result placement* (source order) is a real
  correctness decision that only Pi and Claude Code get explicitly right [3][17].
- Context management is a **spectrum, not a binary**: cap tool output at record time → prune
  historical tool results → summarize → drop to a fresh window. Production harnesses run at least
  three of those simultaneously (Goose `context_mgmt` crate [49], Codex `TruncationPolicy` +
  compaction [42], opencode `prune` + `keep` + `buffer` [45], Claude Code micro-compact /
  context-collapse / auto-compact [17]).
- Compaction thresholds are all *token-budget* maths against `context_window − reserve`; the reserve
  is 16 384 in Pi [6], 20 000 buffer in opencode [47], and `usable()` in Claude Code is derived from
  model + gateway [16]. Overflow is detected by **string-matching provider errors** almost
  everywhere; Pi's ~30-provider pattern table is the reference list [11], OpenClaw's is "dozens" [27].
- Sessions are **append-only logs of typed entries** with `id`/`parentId`, which is what makes
  branching, resume, rewind and fork cheap (Pi `/tree`+`/fork`+`/clone` [8], Claude Code per-project
  `.jsonl` [20], OpenHands lineage stamps [36], OpenClaw writer-claim fencing over SQLite [26]).
- Permissions are a **chain, not a switch**: schema → `validateInput` → rules → approval/judge → OS
  sandbox. Codex is the only one with a declarative policy language (`prefix_rule` in Starlark, with
  `match`/`not_match` as load-time tests) [43]; Claude Code spends >9 000 lines on six layers inside
  BashTool alone [18]; Goose puts an **LLM judge** over the pending batch [49]; Pi declines to
  sandbox at all and says why — which is the most useful sentence in its security doc [9].
- Streaming architecture is the difference between a responsive TUI and a spinner. The pattern worth
  copying is *pipelined tool execution*: start a tool as soon as its input block closes, don't wait
  for the assistant message to end [17][4].
- Cost accounting needs **four numbers plus a cache split** (`input`, `output`, `cacheRead`,
  `cacheWrite`, `cost.total`) recorded *per entry*, including entries generated by compaction and
  subagents — otherwise summarization and delegation are invisible in the bill [14][41].
- Continual learning, in one existing implementation: OpenClaw runs a **silent memory-flush turn**
  before compaction so the agent writes durable notes to disk *before* the context that produced
  them is thrown away [27]. That is the cheapest self-improvement loop available and Aiden should
  copy it in week one.

## Anatomy of a harness: the layers

```
                       ┌──────────────────────────────────────────────┐
   user / channel /    │ L0 Interface      TUI · CLI · RPC · webhook   │
   CI / other agent ──▶│   steer queue · follow-up queue · interrupts  │
                       └───────────────┬──────────────────────────────┘
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│ L1 Prompt assembly   system prompt + context files + skills + tool schemas      │← cache-stable
│                    ─────────────────────────────────────────────────────────────┤   prefix
│ L2 Model transport   provider stream · retry/backoff · overflow detection       │
│ L3 Turn loop         assemble → stream → parse tool_use → gate → execute → loop │
│ L4 Tool plane        schema → validateInput → policy → approval → sandbox       │
│ L5 Context lifecycle cap(prune) → compact → reset  + external memory files      │
│ L6 Session store     append-only entry log (JSONL/SQLite) · branch · resume     │
│ L7 Delegation        child sessions/agents · lanes · completion handoff         │
│ L8 Guardrail/security project trust · hooks · classifier · OS sandbox           │
│ L9 Accounting        per-entry usage · cost breakdown · budgets · telemetry     │
└─────────────────────────────────────────────────────────────────────────────────┘
                                       ▼
                       files · shell · MCP servers · browser · containers
```

### L0 Interface: queues, not prompts

A harness accepts input while it is already running. Pi makes this explicit with two distinct
drain points — `getSteeringMessages()` polled inside the tool loop and `getFollowUpMessages()`
polled only when the loop is about to exit — plus `QueueMode = "all" | "one-at-a-time"` to decide
how much of the queue is injected at once [3]. OpenClaw generalises it to per-session + global
**lanes** with queue modes `steer | followup | collect | interrupt`, and refuses to let a
superseded run commit transcript writes at all (writer claim `activeWriterRunId` checked inside the
commit transaction) [26]. Design consequence: the interface layer must be able to *pre-empt* the
loop, which is why the loop must be a state machine with named resumable points, not one long
`await`.

### L1 Prompt assembly

Ordering is a caching decision. Claude Code splits the prompt into two memoized contexts precisely
because they expire at different rates: `getSystemContext()` (git state, cache breaker) and
`getUserContext()` (CLAUDE.md, date), each with its own `cache_control` treatment [19]. Pi builds
one string but keeps it structurally stable: tool list → guidelines → `<project_context>` with
`<project_instructions path=…>` blocks → skills index → `cwd` [5]. Aider assembles per-message:
repo map + read-only files + in-chat files + fenced file blocks, and the repo map is *scaled by
what's already in context* (`map_mul_no_files` when nothing is added) [31][32]. Goose renders a
MiniJinja template plus per-extension instructions, and keeps a separate `tiny_model_system.md`
for weak models [49]. OpenHands composes `AgentContext` from skills with **trigger types**
(always-on, `KeywordTrigger`, `TaskTrigger`) so context is injected by predicate, not by position [36].

Rule of thumb that all nine implementations agree on: the system prompt is *stable and small*;
volatile facts (git status, todo state, active-subagent table) go in user-role or system-*fragment*
messages so the cached prefix survives. OpenClaw injects an `Active Subagents` block per turn and
quotes task/label fields **as data, not instructions** — a prompt-injection discipline worth copying
verbatim [29]. The same logic applies to tool schemas: Claude Code's tool search defers hundreds of
MCP definitions until they are discovered on demand [23], and Pi's `splitDeferredTools`
(`packages/ai/src/utils/deferred-tools.ts`) keeps only the definitions a transcript has actually used [1].

### L2 Model transport

The failure contract matters more than the API surface. Pi encodes it as a type: `StreamFn` *must
not throw*; provider failures arrive as an `AssistantMessage` with `stopReason: "error" | "aborted"`
and an `errorMessage`, so the loop has exactly one error path [3]. Claude Code's whole pipeline is
an `async function*` chain (`submitMessage* → query* → queryLoop* → callModel* → runTools*`) which
buys the ability to resume mid-stream at seven different recovery points without inverting control [17].
Codex models it as a typed Rust error enum where one variant (`Stream`) is documented as "the session
loop treats this as transient and will automatically retry the turn" — the retry policy lives *in the
error type's doc comment* [44]. OpenClaw's runtime records a per-response terminal diagnostic
(`endTurn: true|false|"absent"|"invalid"`) in the saved message, because "did the model mean to stop"
is not always answerable after the fact [26].

### L3 Turn loop

Same skeleton everywhere:

```
assemble context → stream assistant → extract tool_use blocks
  → for each: validate → gate → (execute | reject)
  → append tool_results → maybe inject steering → loop
  → stop when: no tool calls AND no queued messages AND no recovery reason
```

What differs is how recovery is represented. Four styles seen in the wild:

| Style | Example | Recovery lives in |
|---|---|---|
| Multi-`continue` imperative loop | Claude Code `query.ts` | 7 named `continue` reasons + a 10-field `State` record replaced wholesale (`state = {...}`) so the type system catches missed fields [17] |
| Event-emitting nested loop | Pi `runLoop` | `shouldStopAfterTurn` / `prepareNextTurn` hooks + `stopReason` checks; compaction runs *inside* the run [2] |
| Explicit reducer over named states | Pi durable harness `drive.ts`, Goose `state_machine` | `state.at` (`assistant.ready`, `assistant.retry_wait`, `tools`, `summary.deciding`, `navigation.ready_to_commit`); invariant: a procedure that changes no state throws `SessionInvariantError` [4][49] |
| Event-sourced step | OpenHands `Agent.step(state)` | events + `Condensation` events + `StuckDetector` over the log [35][36][38] |

That last invariant — *assert forward progress* — is the single best bug-catcher for a home-grown
loop, because "spinner that never terminates" is the default failure mode of naive harnesses.

### L4 Tool plane

Two nested phases, and Claude Code names them precisely: `partitionToolCalls()` groups consecutive
`isConcurrencySafe(parsedInput)` tools into parallel batches (concurrency safety is decided **per
call, per input**, not per tool type), then `StreamingToolExecutor` decides at runtime whether a
tool may start (`executingTools.length === 0` or everything involved is concurrency-safe) [17]. Pi
exposes the same split as `ToolExecutionMode = "sequential" | "parallel"` with documented event
semantics: `tool_execution_end` fires in **completion order**, while tool-result *messages* are
appended later in **assistant source order** [3]. Two refinements worth stealing:

- `siblingAbortController`: a child of the turn's abort controller. A failed `bash` cancels its
  siblings (`mkdir && cd && make` is a chain); a failed `read` does not (they are independent) [17].
- Early termination as a *tool result* property: Pi's `afterToolCall` can set `terminate`, and the
  batch stops only when **every** finalized result asks for it — which is how a guard hook can end
  a run cleanly [3].

### L5 Context lifecycle

See the dedicated section below; the layer boundary that matters is that **cap-at-record-time lives
in the tool layer, not the compaction layer**. Goose's `large_response_handler.rs` writes any tool
response over 200 000 chars to an owner-only temp file and substitutes a pointer in context [49];
Codex applies a `TruncationPolicy` while recording items into history (`truncate_function_output_payload`) [42];
Claude Code's `contentReplacementState` does the same thing at 42-tool scale [18].

### L6 Session store

Four shapes: JSONL entry log per session (Pi, Claude Code, Codex rollout, Aider via git), SQLite
transcript with writer fencing (OpenClaw), sharded file event store with count markers (OpenHands),
and per-session worker processes behind a socket server (Pi experimental `mini/server`) [8][20][42][26][36][4].

### L7 Delegation, L8 guardrails, L9 accounting

Covered below; structurally, L7 must be implemented *as a tool* (spawn/join are tool calls) so it
composes with L4's guard chain, and L9 must live *inside the store* (usage per entry) so totals survive resume.

## Context management strategies

Ordered by how early in the pipeline they act. Production harnesses use 1–3 always, 4–6 near-universally.

1. **Cap at record time** (cheapest, lossless-in-principle, reversible): Goose spills >200 000-char
   tool outputs to a file and keeps a pointer [49]; Codex truncates function output payloads while
   writing history [42]; opencode caps tool output at 2 000 chars for summary input [45].
2. **Structural pruning** — keep recent, elide old *tool results* while keeping their existence:
   `LastNObservations(n)` in SWE-agent [53]; OpenHands' `keep_first=2` pins the task and condenses
   the tail [35]; `ops_tool_pair_compaction.rs` in Goose exists to compact a call+result pair as a
   unit [49]. Pi's cut-point rule is the invariant form of the same idea: valid cut points are
   user/assistant/bash-execution/custom messages, **never** a tool result [6].
3. **Explicit cache control as a context strategy**: SWE-agent's `CacheControlHistoryProcessor`
   injects cache breakpoints into history so the stable prefix survives repeated forwards [53].
4. **Summarization (compaction)**: Pi's five-step algorithm (find cut point by walking back to
   `keepRecentTokens` → collect messages from the *previous kept boundary* → LLM summary with a
   structured template → append `CompactionEntry{summary, firstKeptEntryId, tokensBefore, usage,
   details}` → rebuild context as summary + kept tail) is the cleanest published description of the
   mechanics, including the split-turn case where one turn exceeds the budget and two summaries are
   merged [6]. opencode arrives at the same design independently, with the same section skeleton
   (Objective / Important Details / Work State (Completed, Active, Blocked) / Next Move / Relevant
   Files) plus an explicit merge prompt warning the model that "anything you do not carry into the
   new summary is lost" [45]. Claude Code documents what *survives* — the useful part of the spec:
   system prompt and output style still apply, project-root CLAUDE.md and auto memory re-inject from
   disk, plan-mode plan re-injects, up to 5 recently-modified read files are re-read, invoked skill
   bodies re-inject capped at 5 000 tokens each and 25 000 total [16].
5. **Provider-side compaction / checkpoints**: Codex distinguishes `Implementation::Responses` from
   `ResponsesCompactionV2` and treats `CompHashChanged` as its own trigger [41]; OpenClaw preserves a
   compacted window returned by an embedded Responses provider (≤16 MiB) and counts it against the
   prompt budget, falling back to client-side compaction when it is oversized or redacted away [27].
6. **Reset boundaries**: Codex `start_new_context_window` and the `Memento` strategy [41][42];
   Pi `/clear`; Claude Code `/clear` between unrelated tasks [16].
7. **External memory as a compaction pre-step** — the one idea with the highest ratio of benefit to
   effort: OpenClaw inserts a silent memory-flush turn before compacting so the agent writes
   durable notes to `MEMORY.md`/daily files *while it still has the context*, and can pin a
   different (cheaper/local) model for that housekeeping turn [27].

```
  raw history ─▶ cap@record ─▶ prune ─────▶ compact ───▶ reset ─▶ fresh window
  1.2 MB text   spill >200k   old tool      LLM summary  new context
  from 40 reads to file [49]  results,      at cut point window; only
                calls+results keep_first    firstKeptEntry CLAUDE.md / memory
                stay paired [53] +summary kept [6]        [16]
```

Not context management, though often confused with it: subagents (they move cost into a separate
window; the parent still pays for the returned summary [16][18]) and retrieval (changes what you read, not what you keep).

## Session persistence, branching and resume

The universal primitive is an **append-only log of typed entries** where every entry has
`id`/`parentId`, and "resume" means "rebuild the LLM-visible context by walking the path to a leaf
and applying compaction boundaries." Pi's format is the most legible spec: header entry with
version, then `message | compaction | branch_summary | custom | label | session_info` entries, with
v1→v3 auto-migration on load [7]. Rebuild semantics after compaction, in Pi's own words: session
context is rebuilt as system prompt + summary + messages from `firstKeptEntryId` onwards, and on
*repeat* compaction the summarized span starts at the **previous kept boundary**, not at the
previous compaction entry — which is what stops old-but-still-relevant messages from being
permanently flattened into a summary [6].

Branching is where implementations split:

| Model | Mechanism | Trade-off |
|---|---|---|
| In-place tree | Pi `/tree`: same file, navigate leaf, optional `branch_summary` of the abandoned path [8] | Zero duplication; a walk-away turn costs one summarization call |
| New file | Pi `/fork` (from an earlier prompt) and `/clone` (current active branch) [8] | Independent history; no cross-branch context unless summarized |
| Forked session + lineage | OpenClaw `context: "fork"` copies the parent transcript into the child, including in-progress user turn and completed tool results [29] | Cache-friendly child; OpenClaw explicitly reports `isolated` when a requested fork exceeds the parent-context size cap [29] |
| Thread graph | Codex `parent_thread_id` / `forked_from_thread_id` + `agent-graph-store`, with `AgentLimitReached{max_threads}` as a guardrail [41][44] | Subagents are *sessions* with a graph; resumable, inspectable |
| Event lineage stamps | OpenHands `_stamp_parent_id(event)` on the way in, with the authoritative stamp at `ConversationState.append_event` (hooks that swap events get re-stamped) [36] | Lineage enforced at the store, not by callers |
| Git as the store | Aider: every accepted edit is a commit with the prompt as message; `/undo` refuses if HEAD wasn't created by aider in this session [34] | Free diff/review/revert UX; no message tree |
| Rewind via snapshot | Claude Code `/rewind` with "Summarize from here / up to here" [16]; opencode `revert.ts` | Summarize-instead-of-discard beats either extreme |

Missing everywhere: cross-session *semantic* memory as a first-class layer — OpenClaw's memory files
and Claude Code's auto memory are the closest, both file-based rather than DB-based [27][16].

## Subagents and parallel delegation

Three distinct reasons to delegate, and the implementations differ by which they optimise:

- **Context isolation** (dominant reason): Claude Code docs recommend subagents precisely so "the
  large file reads stay out of your context … only the summary and a small metadata trailer come
  back" [16]. Pi's example agents encode roles for this: `scout.md` is "fast recon, returns
  compressed context" [15].
- **Parallelism**: Goose's `subagent_execution_tool` runs fan-out tasks and reports an
  `execution_summary` with per-task status [49][50]; Pi's example streams all parallel tasks
  simultaneously and kills children on Ctrl-C propagation [15].
- **Cost/routing arbitrage**: sub-agent model overrides (OpenClaw `subagents.model`, Pi
  `--model` per agent, Claude Code `model: 'inherit'` *because* a different model breaks the shared
  prompt cache) [29][15][18].

Implementation notes that are non-obvious and directly reusable:

- OpenClaw's fork mode replaces tool results with placeholders so all fork children produce
  **byte-identical prefixes**, forbids recursive forking with a boilerplate tag, and inherits model
  — three constraints that exist only to keep one cache warm for N children [18][29].
- Subagents must not poll. OpenClaw provides `sessions_yield` as the wait primitive (rejecting a
  yield with no real pending child), defers it if earlier async tool results haven't reached the
  model yet, and caps the "recently completed" and "awaiting delivery" blocks at 8 entries [29].
  Aiden's own tool-use guidance should carry the same rule: waiting is a *runtime* operation.
- Delegation is a permission surface. OpenClaw gates `sessions_spawn` on tool profiles and channel
  policy, restricts `cwd` outside agent workspaces to admins, and supports `sandbox: "require"` to
  refuse an unsandboxed child [29]. OpenHands' `delegate` tool is a tool like any other, so the
  same `SecurityRisk` analyzer applies [40].
- Pi's example subagents deliberately shell out to `pi` processes rather than nesting in-process
  agents: it buys crash isolation and true context separation at the cost of cold starts, and its
  README states the security caveat (repo-controlled agent prompts) rather than hiding it [15].
- Subagents stop *early* on budget pressure: Claude Code's token budget check exempts sub-agents,
  which "stop immediately" instead of continuing under a shared budget [19].

## Permission and tool-guard models

The five-stage chain, with the best-in-class implementation per stage:

```
schema ──▶ tool.validateInput ──▶ rules ──▶ hook / approval / judge ──▶ OS sandbox
 TypeBox    Claude Code         Codex      Claude Code hooks         Codex seatbelt/
 [10]        readOnly+path+      prefix_rule  (allow cannot           bwrap [43][44]
             sed validation      [43]         override deny) [19]     Goose sandboxed exec
```

- **Pi** is the minimal honest design: `validateToolArguments` (TypeBox) → `beforeToolCall` gate
  returning `{block, reason, terminate?}` → *no sandbox*, with a `security.md` that explains why a
  partial in-process sandbox is worse than none, and `project_trust` as an input-loading guard
  (a repo cannot silently install extensions or override the system prompt before you say yes)
  [3][10][9]. Note the sharp edge the docs own: `AGENTS.md`/`CLAUDE.md` load *regardless* of trust,
  so the guard covers code, not prompt-injection.
- **Codex CLI** is the declarative-policy design: `AskForApproval` × `SandboxPolicy` are orthogonal
  enums, and the execpolicy DSL is Starlark with `decision = allow | prompt | forbidden` plus
  `match`/`not_match` examples **validated at load time** — policy files with unit tests [43][44].
- **Claude Code** is the defence-in-depth design: 6 layers inside BashTool alone, `buildTool()`
  defaults `isConcurrencySafe=false` / `isReadOnly=false` (fail-closed), and the invariant that a
  hook's `allow` still runs `checkRuleBasedPermissions()` — "hooks are automation helpers, not
  security bypasses" [18][19].
- **Goose** is the classifier design: `permission_judge.md` renders the *pending tool batch* to a
  model, untrusted request text is kept out of the system prompt, and approval is tracked per
  `toolCallId`+arguments rather than per tool name [49].
- **OpenHands** is the risk-tier design: `SecurityRisk` as an ordered enum where `UNKNOWN`
  deliberately cannot be compared, plus an ensemble of analyzers (AST-based shell parsing,
  ToolShield LLM analyzer, gray-swan checks) and a `confirmation_policy` layer [37].
- **OpenClaw** is the multi-tenant design: policy applied per channel/group/agent/sandbox stage,
  plus per-node exec approvals, because the "user" may be WhatsApp [29][30].
- **opencode** is the ruleset design: `{action, resource, effect}` triples with wildcard matching,
  evaluated per agent and merged (`Permission.merge(taskAgent.permission, session.permission)`), and
  a `missingAgentPermissions` default of `deny *` [48].
- **Aider** is the reversibility design: no gates, but every mutation is a git commit and `/undo`
  is the safety net. For a local, single-user, human-present tool this is a legitimate trade —
  and it is why Aider's `main.py` needs no policy engine [31][34].

Aiden should adopt the **chain shape with Pi's honesty**: schema → semantic validation → declarative
rules → hook/judge → optional OS boundary, and treat reversibility (git checkpoints) as a *sixth*
stage rather than a substitute for the first five.

## Streaming architecture

The two decisions that determine perceived latency:

1. **Does the loop emit events or return values?** Pi emits a typed event stream
   (`agent_start`, `turn_start`, `message_start/end`, `tool_execution_start/update/end`,
   `turn_end`, `agent_end`) and reduces state from it, so a TUI, an RPC mode and a JSON mode are
   three renderings of one stream [2][3]. OpenClaw bridges runtime events onto named streams
   (`assistant`, `tool`, `lifecycle`) consumed by heterogeneous clients (WhatsApp, web chat, macOS
   app) [26]. opencode runs SSE over an Effect-based event store; Codex's app-server protocol is the
   same idea in Rust [47][44][25].
2. **When does a tool start?** Claude Code's `StreamingToolExecutor` starts a tool the instant its
   input block closes rather than at end-of-message: with five `ReadFile` calls that is the
   difference between summing and overlapping their latencies [17]. Pi reaches the same place via
   `tool_execution_update` partial results while running batches in parallel mode [3].

Cancellation is the third, most-underestimated decision: hierarchical abort scopes (turn controller →
sibling controller) plus an explicit rule that a cancellation must not resurrect recovery hooks —
OpenClaw states that stopping a run stops its overflow/timeout recovery and that "cancellation is not
rollback": a compaction that already committed stays committed and stays counted [27].

## Tool-call validation, retry and error taxonomy

The universal ordering, assembled from Claude Code's documented pipeline and Pi's implementation:

```
find tool (aliases) → abort check → schema validate → tool.validateInput()
  → speculative classifier (bash only) → PreToolUse hooks → permission resolve
  → execute → PostToolUse hooks (may rewrite result)
```
[17][18]

Pi's equivalent, with the three outcomes that matter: unknown tool → error tool result
(`Tool X not found`); invalid args → `validateToolArguments` throws → captured as an error tool
result; blocked by gate → error tool result with the reason. **Errors are content, not exceptions** —
they go back to the model as a `toolResult` with `isError: true` so the model can adapt [10][3].
One detail with outsized safety value: if the assistant message ended with `stopReason === "length"`,
Pi refuses to execute *any* tool call in it, because every argument may be silently truncated [2].

Retry taxonomy across the nine:

| Class | Detector | Action | Source |
|---|---|---|---|
| Transport/429/5xx | typed error or message regex | exponential backoff + jitter, honour `Retry-After`, bounded attempts (Pi `maxRetries`/`baseDelayMs`/`maxAgentDelayMs` 60 s; opencode 5 tries, 2 s initial, jitter 0.25) | [12][46] |
| Stream drop after handshake | typed variant | retry the *turn*, not the request | [44] |
| Context overflow | ~30 provider message patterns (Pi), "dozens" (OpenClaw), incl. providers that **silently truncate or accept** overflow | compact → retry the aborted turn; Pi detects the silent cases via `usage.input > contextWindow` and `stopReason=length` with zero output | [11][6][27] |
| Format / edit-fidelity failure | parse or apply failure | re-query with the failing artifact echoed back; Aider's `reflection_*` models and SWE-agent's `format_error_template` are the explicit versions | [31][52] |
| Tool denial | gate/block | error tool result + optional `terminate` | [3] |
| Stuck | repeated action/observation cycles, repeated errors, monologue | stop the run and surface it (OpenHands `StuckDetector` thresholds) | [38] |
| Budget | per-session totals vs `--max-budget-usd` / `SessionBudgetExceeded` | stop cleanly with evidence | [22][44] |

Two harnesses teach the *taxonomy-as-data* pattern best: Codex, whose error enum carries retry
semantics in comments and whose execpolicy rules carry `match`/`not_match` test cases [43][44]; and
SWE-agent, whose exception classes (`FormatError`, `FunctionCallingFormatError`,
`ContextWindowExceededError`, `CostLimitExceededError` with per-instance/per-call variants,
`ContentPolicyViolationError`) each pick a recovery: re-query with `format_error_template` echoed
into history up to `max_requeries`, force an autosubmission, or stop [52].

## Cost accounting

Minimum viable schema, as implemented by Pi: `{input, output, cacheRead, cacheWrite,
reasoningTokens?, cost.total}` recorded on every assistant entry, **and** on non-assistant entries
that spend model calls (tool results with `usage`, compaction and branch-summary entries), with
breakdown grouped by `provider/responseModel` and everything else bucketed as "Tools/summaries" [14].
The subtlety that keeps getting missed: `totalTokens` is computed as `input + output + cacheRead +
cacheWrite` (`calculateContextTokens`) — cache read is *not* free context, it is cheap context, and
a compaction estimator that ignores it will under-predict [13].

Layered on top: budgets (`--max-budget-usd` and the status-line cost field [22]; Codex's
`SessionBudgetExceeded` [44]); continuation budgets (Claude Code's `checkTokenBudget` governs *response*
length — continue below 90 % of budget, stop after 3+ turns each adding <500 tokens, and the nudge
message says "do not summarize" [17]); and org-level export via OTel + the Analytics API [22].

For a learning harness the interesting move is Codex's: compaction is instrumented as an event with
trigger, reason, implementation, phase, strategy and status [41]. You cannot tune what you do not
classify, and "which compaction strategy actually preserved the task?" is exactly the question Aiden
must be able to ask later.

## Patterns worth copying

1. **`StreamFn` must not throw** — encode failures as `stopReason` + `errorMessage` so the loop has
   one error path [3]. Pair it with "errors are tool results, not exceptions" [10].
2. **Assert forward progress** in the state machine; a procedure that changes no state is a bug, not
   a wait [4].
3. **Tool-declared metadata with fail-closed defaults**: `isConcurrencySafe(input)`, `isReadOnly`,
   `maxResultSizeChars`, `interruptBehavior`, `validateInput` — one object, no external registries [18].
4. **Cap tool output at record time**, and spill to a file with a pointer instead of truncating into
   oblivion [49][42].
5. **Compact on turn boundaries; never split a call from its result** — then add the split-turn
   escape hatch for single turns that blow the budget [6].
6. **Two summary prompts, not one**: an initial summarizer *and* an explicit merge prompt for
   re-compaction, with "the prior summary is discarded after this" stated to the model [45].
7. **Memory flush before compaction** so durable knowledge survives the flatten [27].
8. **Structured re-injection list** after compaction (project instructions, plan, ≤5 recently
   modified files, skill bodies under a per-skill and total cap) — a documented survival table is
   worth more than a clever algorithm [16].
9. **Hierarchical abort scopes**: a sibling controller so one failed `bash` cancels only its
   siblings [17]; and a rule that cancellation disables further recovery hooks [27].
10. **Declarative policy with load-time test cases** (Codex `prefix_rule(..., match=[...],
    not_match=[...])`) — approval rules become reviewable artifacts, which matters doubly for a
    self-updating harness [43].
11. **A named wait primitive for delegation** (`sessions_yield`) with rejection when there is nothing
    to wait for, instead of a polling tool loop; and when a parent's context genuinely must be shared,
    fork children with **byte-identical prefixes** — placeholders for tool results, inherited model,
    anti-recursion tag [29][18].
12. **Project trust as an input-loading guard**, with honest documentation of what it does *not*
    protect against [9].
13. **Per-entry usage including summary and subagent cost**, bucketed for reporting [14][41].
14. **Prompt-injection hygiene in injected context**: quote dynamic fields (task names, labels, file
    content) as data; keep untrusted text out of the judge/system prompt path [29][49].

## Patterns to skip

1. **Seven `continue` reasons in a 1 729-line `query.ts`.** The resilience is real, but it is
   unmaintainable outside a company-scale codebase; the reducer with named states gives the same
   recovery coverage with testable per-state units [17][4].
2. **A hand-rolled BashTool security stack (6 layers, ~9 400 lines).** Correct for a product; a
   learning harness should use one allow/deny rule engine + an OS sandbox and say so [18][24][9].
3. **In-process recursion for subagents by default.** Forking the parent transcript is a cache
   optimisation that costs a second writer, lineage tracking, and a whole policy surface. Isolated
   children first; fork only where continuity is genuinely required [29][18].
4. **Token estimation by string length as the primary mechanism.** Pi's `CHARS_PER_TOKEN = 4` +
   `ESTIMATED_IMAGE_CHARS` is fine as a *fallback*, but relying on it is why several harnesses need
   provider-overflow string matching at all; prefer the last real `usage` block plus a trailing
   estimate, which is exactly what Pi's `ContextUsageEstimate` returns [13][11].
5. **Regex soup for retryability.** opencode's seven-pattern `RETRYABLE_MESSAGE_PATTERNS` is
   pragmatic but unbounded; a typed error enum with per-variant semantics (Codex) is what a
   self-modifying harness needs, because the agent may edit its own policy [46][44].
6. **Prompt-cache engineering before you have traffic**, and one role list baked into the system
   prompt. Byte-identical fork prefixes and dual-memoized contexts answer Anthropic-specific cache
   pricing — note the mechanism, skip the complexity in v1 [18][19]. Per-agent definition files with
   their own model/tool/reasoning config are the extensible shape, and context *engineering* (curating
   what enters the window) beats compression as the frame for a harness meant to learn [31][15][54].
7. **Silent truncation with no marker.** Every cap must leave a trace (`[truncated N chars]`),
   or the model will reason over a hole it cannot see — Pi and OpenClaw both emit explicit markers,
   including for omitted images [6][27].
8. **Letting compaction write over the transcript as history.** Keep summaries as entries; OpenClaw's
   byte guard exists because provider-side compaction can leave a persisted transcript growing
   separately from the model's window — two ledgers, not one [27].
9. **A permissive `project_trust` that also loads code.** Pi's separation (context files load anyway;
   extensions/prompts/settings require trust) is the right line — don't blur it while "improving UX" [9].

## Implications for Aiden

**Adopt (build in v1):**

- `StreamFn` non-throwing contract + typed event stream as the single source of truth for TUI, JSON
  and RPC modes; the TUI is then a reducer over the same events (Pi's model) [3][2].
- A named-state reducer for the turn loop with an explicit forward-progress assertion [4].
- Entry-log session store (JSONL with `id`/`parentId`, header with a format version) giving
  resume/fork/branch for free; version field first, migration second [7].
- Three-stage context lifecycle: cap-at-record (spill big tool output to a file with a pointer) →
  prune historical tool results keeping call/result pairs → structured compaction with
  `first_kept_entry_id` and an explicit merge prompt [49][6][45].
- **Memory flush before compaction**, as the first continual-learning mechanism: a silent turn that
  appends durable notes (decisions, repo facts, failures) to per-project markdown *while the context
  still exists*, then compaction proceeds [27]. This is also the cheapest dataset for later
  self-improvement analysis, and it needs no new model capability.
- Per-entry usage `{input, output, cache_read, cache_write, reasoning, cost_total}` including
  compaction and subagent usage, with a per-model breakdown [14].
- Tool-declared metadata with fail-closed defaults, and gate hooks returning
  `Block | Mutate | Allow` where denial becomes an error tool result [3][10][18].
- Two input queues (steer / follow-up) with a documented drain mode [3].
- Compaction instrumentation as a classified event (trigger, reason, strategy, phase, status) so the
  learning loop has a signal to optimize against [41].

**Adopt later (behind a flag):** declarative policy rules with load-time `match`/`not_match`
examples [43]; sibling abort scopes [17]; subagents as separate processes with an isolated context
default and a named wait primitive [15][29]; `/rewind` with summarize-from-here [16].

**Skip:** prompt-cache engineering; a home-grown Bash security stack; provider overflow regexes
as the primary defence (keep a small matcher as fallback, seeded from Pi's table) [11]; Aider's
no-gate model (Aiden will *self-modify*, so reversibility is not enough — self-update needs
`project_trust`-style guards, an approval step, and a rollback path); and 42-tool breadth.
Five tools (`read`, `write`, `edit`, `bash`, `search`) plus `task`/`spawn` suffice to learn the mechanisms.

**Architecture consequence for the TUI:** L0 and L9 are only consumers of the event stream and the
entry log, so the TUI is a pure projection — turn/step/tool tree, per-entry token and cost badges,
compaction markers with before/after context size, active-subagent table, budget bar [17][14][29].

## Open questions

1. What is the measured quality loss of compaction on multi-hour coding tasks? Everyone publishes a
   summary *template*; nobody publishes a before/after task-success number [6][45][16].
2. How do Claude Code's "micro-compact" and "context collapse" differ mechanically from Pi's
   compaction — the reverse-engineered posts name them as loop stages without giving thresholds [17].
3. Codex `Strategy::Memento` vs `PrefixCompaction`: the enum is public, the semantics are not
   documented in the repo [41].
4. Do provider-side compacted checkpoints (OpenClaw's 16 MiB preserved window) ever beat
   client-side summarization on cost-to-quality ratio, now that cache reads are cheap-ish [27][13]?
5. Where exactly should an `after_tool_call` rewrite hook be placed when the rewritten result is
   also the cached prefix — invalidate or accept the cache break? No implementation documents this [3][19].
6. Is `stuck` a context-management concern or a loop concern? OpenHands puts `StuckDetector` on the
   conversation, Claude Code puts the diminishing-returns test in the token-budget check [38][17].
7. What is the right concurrency ceiling for a *local* harness? Claude Code caps read batches at 10,
   OpenClaw's example uses `maxConcurrent: 4` — no principled basis published [17][29].
8. How should subagent cost roll up for a *self-updating* harness that spawns its own children:
   per-session, per-tree, or per-attempt? Pi buckets by provider/model but not by agent tree [14][15].
9. Does anyone implement compaction that *keeps* tool results and summarizes assistant reasoning
   instead? All nine summarize oldest-first by position; a content-aware policy is unexplored [6][45].
10. Is context *engineering* (curation, retrieval, durable notes) separable from compression at all
    in a harness meant to learn? Anthropic frames it as the successor to prompt engineering [54].
